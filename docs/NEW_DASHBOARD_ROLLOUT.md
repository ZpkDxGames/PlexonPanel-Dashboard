# Review, cutover and rollback

This candidate is for review only. Production promotion is not authorized by this implementation request.

1. Review the branch/PR, screenshots, parity matrix, final checks and measured regressions/limits.
2. For local review use Node 24.x, `npm ci`, public relay configuration per `.env.example`, and `npm run dev`. Fixture URLs such as `/?fixture=healthy#Overview` work only in development. `npm run build` creates the production artifact; its fixture query must still resolve to pairing for an unpaired browser.
3. A Vercel PR preview may be generated by the existing Git integration. Its existence does not establish an approved relay origin or paired-runtime acceptance. Do not edit the relay allowlist as part of this task. Unapproved preview origins can still be used to review unauthenticated entry behavior; use localhost fixtures for full visual review.
4. Before an eventual authorized cutover, record the then-current production deployment ID/URL, frontend SHA/build identity and public relay/CSP values. Preserve that immutable deployment.
5. Complete read-only acceptance using a disposable least-privilege pairing at an already approved origin: real Paper/Host captures, skew/gaps, disconnected sources, mixed versions, shared-node Fleet and UUID history isolation. Then deliberately review a safe query and confirm the actual agent result/audit.
6. Operational mutation and backup acceptance requires a disposable server, explicit operator coordination and the existing Core runtime gates. Check unknown-outcome behavior, target changes during review, fail-closed preflight and job reconstruction. Do not use a production server just to collect screenshots.
7. Ask for release-specific authorization only after the candidate and remaining live gate results are reviewable. Promote the frontend at the same stable production origin with the same approved relay origin and CSP. IndexedDB is origin-bound: preserve that origin and database identity so existing pairings remain available.
8. Rollback by restoring the previous immutable frontend deployment to the same alias. No backend/state migration is introduced, so no data reversal is necessary. Do not clear IndexedDB or rotate pairings to roll back visuals. If a separate preview pairing was deliberately authorized later, revoke only that pairing and remove only its specifically approved origin after review.
